# Design

## Context

`ci.yml` has four kinds of job that run `npm run build`: `check` (five platforms), `node-range` (two Node versions on Linux arm64), `conformance` (five platforms × two suites) and `threejs` (Linux arm64). `check` alone packs, smoke-tests and, on a releasing run, uploads the tarballs the release publishes. The others test their own builds of the same commit. They share cargo cache keys (`check`, `conformance` and `threejs` all use `cargo-<os>-…`), so whichever saves first owns the entry.

The packed files hold everything the test runners load from `dist/`. The main package holds `dist/**/*.js` and `.d.ts` (package.json `files`). The platform package holds the addon `oxgl.<platform>.node`, `angle/` and `THIRD_PARTY_NOTICES`, the same files `scripts/pack.mjs` copied out of `dist/`. Unpacking both into `dist/` gives a `dist/` the runners and `npm test` accept, built from exactly the published bytes.

The three.js runner already supports platform-limited expectations (`<example> <OUTCOME> [<platform> ...]`), which it shares with the conformance runner. The results page reads one report per suite and platform, keyed by the report's `platform`, and refuses a platform outside the five bundle names (`linux-x64`, `linux-arm64`, `macos-arm64`, `windows-x64`, `windows-arm64`). The conformance report records `hostPlatform()` from `conformance/expectations.mjs`, which gives those names. The three.js report records `${process.platform}-${process.arch}` instead, which matches only on Linux: on macOS it is `darwin-arm64`, and on Windows `win32-x64` and `win32-arm64`.

## Goals / Non-Goals

**Goals:**
- Each platform's addon is built once per run, and every Node, conformance, three.js and GPU test runs against the tarballs the release would publish.
- The three.js examples run and pass in CI on all five platforms.

**Non-Goals:**
- Removing the Rust compilation in `check` (clippy and `cargo test`) or in `asan`.
- Making a test job wait only for its own platform's build.

## Decisions

- **A `build` job per platform that packs and uploads on every run.** It is today's `check` build half: `npm ci`, `npm run build`, `scripts/pack.mjs`, `scripts/smoke-packed.mjs` and, on Linux, `check-glibc.sh`. It uploads `packages-<runner>` on every run, not only releasing ones, because the test jobs need them. A releasing run keeps them 7 days, as today, so a failed release job can be rerun; any other run keeps them 3 days. "Re-run failed jobs" reruns only the failed test jobs, not the `build` that succeeded, so the packages must outlast the gap before a rerun; 3 days covers a weekend. Every leg packs `oxgl-js-oxgl-<version>.tgz` for its smoke test; only `ubuntu-24.04-arm` keeps it, as today, so the run has one, and uploads it as an artifact of its own, `package-main`. Before this change it shared that leg's `packages-ubuntu-24.04-arm` artifact, which only the release read; now every test job reads it, and a separate artifact keeps the platform-independent package apart from one platform's. Alternative: upload `dist/` itself. Rejected: the tarballs are what ships, and unpacking them tests the packing too.
- **Test jobs unpack the tarballs into `dist/` with a script.** `scripts/unpack-packages.mjs <dir>` first unpacks the single `oxgl-js-oxgl-<version>.tgz` and copies its `dist/` into `dist/`. It then imports `platformString` from that freshly unpacked `dist/resolve-native.js`, the code that will load the addon, so the platform name has one definition. The import is dynamic, since `dist/` does not exist when the script loads, and names the module as `new URL('../dist/resolve-native.js', import.meta.url)`: `import()` of an absolute Windows path such as `C:\…` fails with `ERR_UNSUPPORTED_ESM_URL_SCHEME`. With it, it unpacks the host's `oxgl-js-<platform>-<version>.tgz` and copies its addon, `angle/` and `THIRD_PARTY_NOTICES` into `dist/`. Each tarball is extracted by the system `tar` into a temporary directory: the script runs `tar -xzf -` with that directory as its working directory and pipes the archive to its standard input. `tar` then gets no path argument. GNU tar, which Git Bash puts first on Windows runners' `PATH`, reads an archive path such as `C:\…` as a remote host, and both the archives (`$RUNNER_TEMP`) and the temporary directory are absolute paths. Every runner image's `tar`, GNU or bsdtar, reads gzip from standard input. The script fails when either tarball is missing or there is more than one candidate. Alternative: install the tarballs into a scratch project and point the runners at it. Rejected: `conformance/run.mjs`, `threejs/run.mjs` and the tests import the repository's `dist/`, and changing that touches every runner for no gain.
- **Each test job downloads two artifacts.** `package-main` and `packages-<runner>`, merged into one directory with download-artifact's `pattern` (`{package-main,packages-<runner>}`) and `merge-multiple`. A local composite action, `.github/actions/use-packages`, holds the download and the unpack, and `.github/actions/install-ffmpeg` the per-OS ffmpeg install, so each is written once for `node-test`, `conformance` and `threejs`. zizmor's `self-repository` audit, which asks for the `$/…` form of local actions, is disabled: the pinned actionlint rejects that form. The GPU job runs on a self-hosted runner of any platform, so it downloads `package-main` and every `packages-*`, and the script picks the host's. Like every test job, it gains `build` in its `needs`, so it starts only once the packages are uploaded.
- **`check` keeps lint and Rust tests and starts at once.** `lint:rust`, `lint:js` and `cargo test` need no addon build: `lint:js` type-checks `src/` and `test/`, not `dist/`. `check` no longer installs ffmpeg, which only the harness tests need.
- **`node-test` replaces `check`'s `npm test` and `node-range`.** It runs on the five platforms on Node 24, plus Linux arm64 on 22.22.2 and 26 through `include`. It installs ffmpeg for the harness tests, sets up the leg's Node once, and runs `npm ci`, unpacks and runs `npm test` on it. `node-range` installed on Node 24 and then switched because the build tooling needs a newer Node; with no build, that reason is gone, and every devDependency's `engines` accepts 22.22.2.
- **Separate cargo cache keys.** `build` uses `cargo-build-<runner>-…` (release profile) and `check` uses `cargo-check-<runner>-…` (debug and clippy), so neither evicts the other. The other test jobs no longer install Rust or restore cargo or ANGLE caches. The ANGLE cache is kept in `build`, `check` and `asan`.
- **`threejs` becomes a matrix over the five runners.** It installs ffmpeg as `conformance` does (`apt-get`, `brew` or `choco` by `RUNNER_OS`, under `shell: bash`), since the runner refuses to start without it, and uploads `threejs-results-<runner>`. The `results` job's download pattern becomes `{conformance-results-*,threejs-results*}`, which also matches older `main` runs' single `threejs-results` artifact for page-only rebuilds.
- **The three.js report records `hostPlatform()`.** It is the name the expectations and the results page already use, and the conformance report already records it. Alternative: map Node's names in the results page. Rejected: the report would then name its platform differently from the expectations that judged it.
- **Pinned trees are checked out without line-ending conversion.** `ensureCheckout` (`conformance/suite.mjs`), which fetches both the conformance suite and the three.js release, runs its `checkout` with `-c core.autocrlf=false -c core.eol=lf`. Git for Windows commonly sets `core.autocrlf=true`, which would serve CRLF copies of text assets on Windows only: a different byte count for the parse allowance, and a stray `\r` for loaders that split lines on `\n`. Windows-only differences then come from oxgl or SwiftShader, not from the fetch, and the user's VM and the CI runner fetch the same bytes whatever their Git configuration. Caches may already hold converted copies, so the CI cache keys gain an `-lf` suffix, and a developer's Windows `.cache/` copy fetched before this change is deleted once. Alternative: a `.gitattributes` in the scratch repository. Rejected: the command-line settings are one argument and override every config level.
- **macOS runner limits follow conformance if needed.** The conformance job gives macOS `--timeout 180` because `macos-15` runners are slow. The three.js job uses the same flag on macOS only if the PR's CI shows examples timing out there that pass with a longer limit.
- **Platform differences are compared on the same commit.** For macOS arm64, the full suite runs on a developer Mac. For Windows arm64, it runs in a Windows 11 arm64 VM on that Mac. Each report is compared with Linux arm64 example by example. Before attributing a difference, the differing example is re-run alone (`--jobs 1`), so a runner slowdown is not mistaken for a rendering difference. A difference is fixed when it is an oxgl or runner bug, and otherwise recorded as a platform-limited entry with its cause for the user to agree. Linux x64 and Windows x64 are compared the same way from the pull request's CI reports.

## Risks / Trade-offs

- [Every test job waits for the slowest platform's build] → `needs: build` on a matrix job waits for every leg. The critical path is about the same as today, since every conformance leg built the addon itself before testing. A slow Windows arm64 build now also delays the Linux legs' tests. Accepted. Out of scope says how to remove it.
- [Local machines differ from CI runners] → A developer Mac and a VM are not `macos-15` or `windows-11-arm`. Both run SwiftShader, whose output depends on the CPU architecture and compiler more than on the machine. Any remaining CI-only difference shows up in the pull request and is handled then.
- [Linux arm64's build is a single point for the main package] → If its build fails, every platform's tests are skipped. They could not test the published main package anyway, and `ci` fails, as it should.
- Safety rules: no native code changes. The workflow, the unpack script and any runner changes are JavaScript or YAML and touch no `unsafe` code, handles or ArrayBuffer lifetimes. A fix to oxgl found by the comparisons would be designed and reviewed before it is made.
