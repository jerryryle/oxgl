# Design

## Context

The survey's only Windows failures are in the conformance harness's own tests, on both Windows architectures. Two causes:

- `conformance/pool.mjs` classifies a page process that exits by itself with a non-zero code as a native abort only for code 3 (the C runtime's `abort()`) or an `0xC…` NTSTATUS. Node's `process.abort()` on Windows runs `ABORT()`, which ends in `_exit(ExitCode::kAbort)`, 134 (`src/util.h` and `src/node_exit_code.h` at Node v24.11.1). The `abort.html` fixture calls `process.abort()`, so it reaches the last branch and becomes a harness error. `abort-at-teardown.html` aborts the same way; its failure was hidden because the test stops at the first failed assertion.
- The repository has no `.gitattributes`, so Git for Windows' default `core.autocrlf=true` checks text files out with CRLF.

## Goals / Non-Goals

**Goals:**
- Build and test green on Windows x64 and Windows arm64.
- A per-page conformance comparison with Linux arm64 on each Windows platform.

**Non-Goals:**
- Re-enabling Windows in CI (linux-arm64-focus 4.5).
- Testing the D3D11 GPU backend.

## Decisions

- **Treat exit code 134 as an abort on Windows.** It is the code Node itself uses for an abort, so a Node abort and a native one (code 3 or an NTSTATUS, for example from ANGLE or the addon) are both `CRASH`. Alternative: inspect stderr for Node's backtrace. Rejected: fragile, and the exit code is already the runner's signal. A page that calls `process.exit(134)` would also count as a crash; no conformance page can call `process.exit`, so the overlap is harmless. The rule stays Windows-only, since on POSIX an abort arrives as `SIGABRT`.
- **Repository-wide `* text=auto eol=lf`** instead of an exception for one fixture. Every text file then has the same bytes on every host: fixtures, the expectations file, and sources that formatters and linters check. Git detects binary files (PNG, JPEG, the ANGLE archives are not tracked), so they are untouched. A `-text` rule for `served.txt` alone would fix the one test and leave the next fixture to fail the same way.
- **Survey on a scratch branch, as in linux-arm64-focus 4.2.** A workflow of its own, never merged, that does not run the regular CI: build and test on `windows-2025` and `windows-11-arm` until green, then both conformance suites on each Windows runner and on `ubuntu-24.04-arm` in the same run, so every comparison is between outcomes on one commit. ffmpeg is installed on the Windows runners for the video pages. When port-windows and port-linux-x64 are applied together, one scratch workflow with a platform matrix serves both, with one Linux arm64 reference leg.
- **Runner speed is ruled out before a difference is attributed.** Before attributing a difference, re-run each differing page alone (`--jobs 1`) with a long limit (`--timeout 120`) on the same runner: a page that then passes is slow on that runner, not different, as with the macOS comparison (linux-arm64-focus task 4.3). Record those pages too, with their longest gap at the default settings and alone, for the CI decision in linux-arm64-focus task 4.6. GitHub's Windows arm64 runners are likely the slowest of the set.
- **Keep each JIT routine's sections in one reservation.** On arm64, LLVM 10's RuntimeDyld (SwiftShader's legacy object-linking layer) asks the memory manager for code and read-only data separately, and SwiftShader's `MemoryMapper` ignores the placement hint, so the two can land more than 4 GB apart; the `ADRP` relocations that reach the constants then wrap without an error (an `assert` on ELF, nothing on COFF). The patch replaces `SectionMemoryManager` with a memory manager that reserves one block per routine for its code, read-only and read-write sections, so every `ADRP` stays in range on every OS. It also turns an out-of-range `ADRP` into a fatal error in LLVM's relocation code, so a regression aborts instead of reading the wrong memory. Alternative: pad allocations or retry until the sections land close. Rejected: padding does not address the cause (the faulting page is unmapped, not short), and retrying only makes the failure rarer. The patch carries a Reactor unit test and goes in the oxgl-angle recipe like the filtering patch, with a new bundle version.
- **Give ANGLE's integer stand-in textures `NEAREST` filters.** In `IncompleteTextureSet::getIncompleteTexture` (`src/libANGLE/renderer/renderer_utils.cpp`), the integer stand-ins get `NEAREST` min and mag filters, so sampling them with `texture()` no longer asks the backend to filter an integer format. The fix is in ANGLE, where the undefined filtering is requested; SwiftShader's denormal flushing is legitimate for float math. The patch carries `IncompleteTextureTestES3.IntegerTypeFilteredSample`, which samples incomplete `isampler2D` and `usampler2D` textures with `texture()` (the existing tests use `texelFetch`, which skips filtering). A sampler object bound to the unit still overrides the stand-in's filters; the patch's README row names that gap.
- **An expectations entry may list the platforms it applies to.** The format becomes `<suite> <path> <OUTCOME> [<platform> ...] # <reason>`, where the bracketed list is optional and each platform is one of the bundle names `linux-x64`, `linux-arm64`, `macos-arm64`, `windows-x64` and `windows-arm64`, the host's being derived from `process.platform` and `process.arch`. An entry without a list applies everywhere, as today. A listed entry applies only on its platforms; elsewhere the page is judged as if it had no entry. A page may have several entries in a suite when each has a list and the lists do not overlap, so outcomes can differ by platform; an entry without a list stays the page's only entry. An update run treats an entry without a list as listing all five platforms (and writes a list of all five as no list), so a run on one platform never removes an entry the others rely on. It leaves entries that do not apply untouched. On a listed platform it drops that platform from the page's entry when the page now passes or has a different outcome (removing the entry when no platform remains), then records a non-`PASS` outcome by adding the platform to the page's entry with that outcome, or to a new entry for that platform alone when the page has listed entries. A failure on a page with no entries gets an entry without a list, as today, which the developer narrows by hand. Alternatives: one expectations file per platform (rejected: every shared entry would be repeated five times and drift), or per-architecture tags such as `x64` (rejected: the stencil failure followed OS and compiler, not architecture, so architecture alone is not enough in general). Chromium's expectation files use the same idea, with tags per entry.
- **Animation frames wait for every live context's queued work.** At the start of each animation frame, the runner calls `finish()` on every live WebGL context of the page or worker, before compositing and before the frame's callbacks. A browser bounds queued GPU work through frames in flight and command-buffer flow control; oxgl runs in-process with neither, so a page drawing in an animation-frame loop could queue work without limit. Measured locally, `texture-switch-performance` went from 8 s to 5 s alone and from 21 s to 5 s with 16 copies at once; in CI it stalled for over 180 s on `macos-15` and starved the pages beside it. Alternatives: back-pressure inside oxgl's draw path (rejected for now: it changes behaviour for every user and needs its own design, while the runner is the browser stand-in that lacks the bound), or a fence that allows two frames in flight (rejected: one frame is simpler and enough). `many-draw-calls` does real work (about 505,000 draws) and is unaffected.
- **Conformance differences are fixed or agreed, not silently accepted.** A Windows-only difference that is an oxgl bug is fixed in this change (added to tasks and reviewed first). One caused by ANGLE or SwiftShader on Windows is recorded with its cause for the user to agree, and how such platform-specific expectations are stored is proposed then, because the expectations file has no platform field today.

## Risks / Trade-offs

- [Renormalizing line endings touches files committed with CRLF] → `git add --renormalize .` shows any such file in the same commit; if none exist, the commit only adds `.gitattributes`.
- Safety rules: no native code changes. The runner and test changes are JavaScript and touch no `unsafe` code, handles or ArrayBuffer lifetimes.

## Accepted trade-offs

- A page process that exits with code 134 for a reason other than an abort is reported as `CRASH` on Windows. Conformance pages cannot call `process.exit`, so this does not happen in practice.
- Only animation frames wait. A page that draws from `setTimeout` callbacks can still queue work without limit, where a browser's command-buffer flow control would block it; no suite page is known to stall that way, so the runner does not wait at other task boundaries.
- Waiting each frame keeps one frame of GPU work in flight, where a browser allows two or three, so a page that measures its frame rate sees a GPU-bound rate. That is what the measurement is meant to capture.
- `texture-switch-performance` compares two frame rates against a 0.8 ratio. Before the per-frame wait it landed at 0.79–0.80 on the Linux x64 runner, where its backlog grew while it measured; its `SKIP [linux-x64]` entries stay only until CI shows it passing with the wait (task 3.5).
